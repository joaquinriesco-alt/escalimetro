## Problema

CREAR PLANO es core (D-001) pero hoy no existe. Necesitamos aprender rápido qué combinación de
modelo/pipeline reconstruye una planta comercial útil desde evidencia inmobiliaria imperfecta,
sin perder trazabilidad ni engañarnos mirando el plano real antes de tiempo.

El problema de E37 **no es encontrar ya el motor ganador**. Es construir el instrumento de
experimentación que permita comparar A/B/C de forma reproducible y medir cuánto trabajo humano
hace falta para llegar a una planta publicable.

### Benchmark histórico que E37 debe preservar como referencia, no como verdad actual

En una prueba interactiva anterior (2026-08-16), **Piso Ricardo Lyon I, Providencia**:
- 34 fotos;
- 1 nivel;
- 2 dormitorios + 2 baños;
- 76/87 m²;
- plano real disponible como ground truth.

La prueba entendió bien la semántica pero no suficientemente la geometría: inventario de recintos
~9/10; 2D/2B correctos; conexiones ~80%; posiciones relativas ~60–65%; forma global ~55–60%;
proporciones ~50%. Falló especialmente dormitorio 2, la franja de baños, walk-in closet, terraza
y la organización rectangular real. La conclusión útil fue: **el cuello de botella no era saber
qué recintos existen, sino ensamblarlos geométricamente**.

Se propusieron entonces líneas A/B/C con reconstrucción visual/geométrica (COLMAP,
Plane-DUSt3R por recinto y ensamblaje completo), pero no se construyeron. El modelo exacto usado
en aquella sesión no quedó registrado de forma fiable. Por eso esos porcentajes son sólo
**baseline histórico**, no evidencia del modelo actual.

## Resultado esperado

Una ruta interna, preferentemente `/lab/reconstruction/`, en la que Joaquín pueda:

1. crear un proyecto;
2. subir fotos y, opcionalmente, video y datos declarados;
3. subir un plano real como **GROUND TRUTH HIDDEN FROM ENGINE**;
4. elegir un motor registrado;
5. ejecutar una reconstrucción;
6. ver una planta esquemática + representación estructurada + incertidumbre;
7. calificarla `EXCELENTE / BUENO / MALO / PESIMO`;
8. escribir una corrección como «el dormitorio principal era más grande»;
9. obtener una **nueva corrida hija**, sin sobrescribir la anterior;
10. comparar 2–3 corridas lado a lado;
11. revelar el ground truth sólo mediante acción explícita;
12. volver otro día y encontrar toda la historia persistida.

### Contrato mínimo de una reconstrucción

La fuente de verdad no es una imagen generada. Cada corrida debe guardar una representación
estructurada suficiente para regenerar la vista, con al menos:
- recintos/labels;
- relaciones de adyacencia/conectividad;
- posición relativa;
- geometría aproximada normalizada o equivalente explícito;
- puertas/conexiones conocidas cuando haya evidencia;
- incertidumbre/confianza y qué evidencia sustenta cada inferencia relevante.

El renderer puede ser SVG/HTML u otra solución simple. **No usar image generation como fuente de
verdad geométrica.**

### Registro de motores

A/B/C no se hardcodean en la UI. Crear un registry/adapters con metadatos:
`engine_id`, nombre, versión, provider/model/pipeline, disponibilidad, capacidades y parámetros.

E37 debe dejar el sistema listo para añadir después motores como:
- VLM directo;
- VLM + reconstrucción geométrica;
- COLMAP / Plane-DUSt3R / depth / otros pipelines.

Como primer baseline real, implementar un adapter **OpenAI multimodal directo** configurable para
`gpt-5.6-sol` (o model ID configurable por entorno) que reciba las fotos y datos permitidos y
devuelva el contrato estructurado. Debe quedar desacoplado del dominio y testeable con provider
mock.

**No ejecutar llamadas pagadas automáticamente durante tests, startup ni migraciones.** Si falta
`OPENAI_API_KEY`, el motor aparece `UNAVAILABLE / MISSING_CREDENTIAL`, nunca se simula éxito.
Una llamada real sólo ocurre por acción explícita del operador en la UI.

No hace falta implementar COLMAP/Plane-DUSt3R en E37. El registry debe permitir agregarlos sin
reescribir la UI ni el modelo de datos.

## Acceptance criteria

1. **Handoff.** Antes de implementar, verificar según protocolo §5.2 que esta rama sale de
   `m01_1_remote_truth` y que el diff inicial contiene sólo `tasks/E37.md`.

2. **Aislamiento.** `git diff 6324b1f HEAD -- src/` sigue vacío. E37 no modifica el motor
   histórico.

3. **Proyecto persistente.** Se puede crear un Reconstruction Project con nombre y assets.
   Fotos son input principal; video y metadata pueden almacenarse aunque un motor concreto no los
   consuma todavía. Soportar al menos el caso histórico de 34 fotos sin límites artificiales
   menores.

4. **Ground truth ciego.** El ground truth puede cargarse al crear/editar el proyecto pero queda
   separado y marcado `HIDDEN_FROM_ENGINE`. Tests adversariales prueban que ningún adapter recibe
   path, bytes, hash derivable, metadata descriptiva ni contenido del GT antes de reveal.

5. **Runs inmutables.** Cada ejecución persiste ID, project, engine/version, parent_run_id,
   inputs permitidos, prompt/version, parámetros, código/commit cuando corresponda, timestamps,
   estado, output estructurado, artefactos, latencia, costo si se conoce y error si falla.
   Re-ejecutar o corregir crea otra run.

6. **Registry.** Agregar/quitar un adapter no requiere cambiar la lógica de la UI. La UI lista sólo
   motores registrados y distingue AVAILABLE / UNAVAILABLE con razón.

7. **Baseline multimodal.** Existe un adapter real desacoplado para OpenAI multimodal con model ID
   configurable (baseline inicial `gpt-5.6-sol`). Sin credencial no llama red y reporta
   `MISSING_CREDENTIAL`. Tests usan mock/fake transport; cero gasto de API en suite.

8. **Salida útil.** Una run exitosa muestra simultáneamente:
   - plano esquemático renderizado desde la representación estructurada;
   - lista de recintos;
   - conexiones/adyacencias;
   - incertidumbres relevantes;
   - provenance del motor/modelo/prompt.
   Si el motor no tiene evidencia suficiente, puede devolver `INSUFFICIENT_EVIDENCE`; eso es un
   resultado válido y no se maquilla.

9. **Evaluación humana.** Cada run admite exactamente una evaluación vigente
   `EXCELENTE / BUENO / MALO / PESIMO` + comentario opcional, con historial/auditoría si se
   modifica.

10. **Corrección por prompt.** Desde una run se puede escribir una corrección en lenguaje natural.
    El sistema crea una child run con el prompt original guardado. El adapter recibe la
    representación anterior + la instrucción y debe producir una representación estructurada nueva.
    No se edita la imagen directamente.

11. **Ambigüedad.** La interfaz/contrato permite que un motor responda
    `CLARIFICATION_REQUIRED` en vez de adivinar una corrección ambigua.

12. **Comparación.** Se pueden seleccionar 2–3 runs del mismo proyecto y ver lado a lado al menos:
    plano, motor/versión, rating, rooms, prompts humanos acumulados, latencia y costo cuando exista.

13. **Reveal explícito.** Sólo una acción humana `REVEAL GROUND TRUTH` cambia el estado del
    proyecto. Después se muestra GT junto a las runs, pero las runs previas siguen inmutables y
    marcadas como generadas en blind mode.

14. **Métricas 90/10.** El proyecto calcula sin inventar:
    - número de prompts humanos;
    - tiempo humano si fue registrado;
    - rating final;
    - `did_need_manual_CAD` sí/no;
    - rooms detectados/esperados cuando GT fue revelado o etiquetado;
    - juicio humano de adjacency / relative position / geometry usefulness si no hay métrica
      automática fiable.
    No crear un score compuesto arbitrario.

15. **Caso Ricardo Lyon preparado.** La UI y modelo de datos permiten recrear el benchmark histórico
    como proyecto (34 fotos + GT oculto). No hace falta que Claude posea esas 34 fotos en E37; sí
    debe demostrar con fixtures que 34 assets funcionan y documentar cómo cargar el caso real.

16. **Persistencia/historia.** Reiniciar la app no borra proyectos, runs, evaluaciones ni reveal.
    Una run nunca cambia silenciosamente por volver a abrirla.

17. **No contaminación.** E36 y E17 siguen funcionando y sus conteos/métricas no incorporan
    Reconstruction Projects ni runs de E37.

18. **UX interna simple.** Flujo visible:
    `PROYECTOS → NUEVO PROYECTO → INPUTS/GT OCULTO → MOTOR → GENERAR → RESULTADO → CALIFICAR →
    CORREGIR → NUEVA RUN → COMPARAR → REVEAL GT`.
    No exponer jerga técnica innecesaria en el camino principal.

19. **Tests.** Agregar tests unitarios/integración para aislamiento GT, inmutabilidad, registry,
    provider mock, corrección hija, reveal, persistencia y no contaminación. Suite completa sin
    regresiones nuevas; los dos fallos históricos pueden permanecer sólo si siguen siendo
    exactamente los mismos.

20. **Evidencia visual.** REPORT incluye screenshots del flujo real interno con datos fixture:
    proyecto, resultado, child run por prompt, comparación y GT antes/después de reveal.
