# M05 — Estado visible del ejecutor

## Decisión aprobada

Joaquín aprobó mejorar la observabilidad del circuito automático antes de seguir con nuevas TASKs
de producto.

Objetivo:

> **Automático, pero visible.**

Cuando una TASK corre, Joaquín debe poder abrir su issue y distinguir sin ambigüedad:

- ESPERANDO
- TRABAJANDO
- VERIFICANDO
- PUBLICANDO
- TERMINÓ
- FALLÓ

Mirar el estado debe ser opcional. El circuito debe seguir funcionando sin intervención humana.

M04 intentó abordar el mismo objetivo pero el agente no alcanzó a implementar nada. M05 reemplaza
ese intento con una especificación más pequeña y operacional.

## Problema

Hoy GitHub Actions muestra durante varios minutos un único paso largo llamado
`Claude ejecuta la TASK`. Para Joaquín eso no permite distinguir una ejecución activa de un
proceso detenido.

También existe un defecto ya observado en E38: una ejecución con cero commits puede terminar con
el job de publicación verde y un mensaje poco claro.

Necesitamos una señal de estado simple, mantenida por GitHub, que diga qué etapa está ocurriendo y
cuál fue el resultado real.

## Contexto canónico

- Base: `auto/e40-issue-6`.
- Workflow: `.github/workflows/escalimetro-auto-task.yml`.
- Verificador: `scripts/auto_task.py`.
- Protocolo: `docs/ai-development/DEVELOPMENT_PROTOCOL.md`.
- Estado: `docs/ai-development/CURRENT_STATE.md`.
- E38 run `36927264632`: cero commits y `VERIFY NOTHING`.
- E39 y E40 publicaron correctamente un commit real.
- M04 run `36940026024`: no produjo commits; no reutilizar su rama como base.
- Esta TASK es de infraestructura. No modificar producto.
- Los cambios al workflow sólo quedarán activos para ejecuciones futuras después de que Joaquín
  autorice incorporarlos a la rama por defecto.
- `src/` permanece congelado.

## Resultado esperado

### 1. Comentario de estado único

El issue de transporte debe contener un comentario claramente identificable como estado de
ejecución. Durante una misma TASK se debe **actualizar ese comentario**, no crear un comentario
nuevo en cada refresco.

Debe mostrar como mínimo:

- TASK ID;
- estado global;
- etapa actual;
- hora de inicio;
- última actualización;
- link al run;
- gate;
- ejecución del agente;
- verificación;
- publicación;
- al terminar: número de commits, número de archivos, REPORT sí/no y rama publicada;
- `Auditoría ChatGPT: pendiente` al terminar la automatización.

Ejemplo conceptual:

```
E41 — TRABAJANDO
✅ TASK validada
✅ Runner listo
🔵 Agente implementando · 08 min
○ Verificación
○ Publicación
○ Auditoría ChatGPT
```

### 2. Heartbeat

Mientras el agente esté ejecutándose, actualizar el mismo comentario aproximadamente cada 60–120
segundos con tiempo transcurrido y timestamp reciente.

La señal debe basarse sólo en hechos que GitHub/runner conoce. No inventar nombres de archivos,
tests o sub-etapas que el runner todavía no pueda observar.

### 3. Estados posteriores

Al terminar la ejecución del agente:
- estado pasa a VERIFICANDO;
- luego PUBLICANDO;
- finalmente TERMINÓ o FALLÓ.

Si no existe ningún commit producido por una TASK que llegó a la etapa de implementación, el
resultado visible debe ser **FALLÓ / NO_OUTPUT**, no éxito.

Endurecer el flujo para que `VERIFY NOTHING` no deje una ejecución de implementación globalmente
verde. Mantener una semántica clara y testeada para este caso.

### 4. Step Summary

Los jobs relevantes deben escribir un `GITHUB_STEP_SUMMARY` breve con TASK, etapa, resultado y
evidencia principal.

### 5. Contenido permitido

La superficie de estado sólo necesita metadatos operacionales:
- nombres de etapas;
- status/conclusion;
- timestamps y duración;
- conteo de commits/archivos;
- nombres de archivos versionados si ya están disponibles y son apropiados;
- rama, REPORT y resultados de tests ya producidos como evidencia;
- errores sanitizados.

No copiar al comentario el contenido completo producido por el agente ni valores de credenciales,
variables protegidas o datos privados del producto.

### 6. Tests

Agregar tests para:
- render queued;
- render running;
- render verifying;
- render success;
- render failure;
- render NO_OUTPUT;
- actualización del mismo comentario;
- comportamiento del verificador con cero commits;
- preservación de los controles existentes del ejecutor.

No hace falta consumir una llamada adicional al agente para probar el renderer.

## No hacer

- NO tocar landing ni producto.
- NO tocar pricing, estilos ni PRO.
- NO modificar `src/`.
- NO tocar Railway.
- NO deploy.
- NO merge a `main`.
- NO auto-merge.
- NO agregar servicios externos.
- NO agregar una UI externa: GitHub issue + Actions + Step Summary son suficientes para v1.
- NO ampliar permisos más de lo necesario.
- NO imprimir credenciales ni variables protegidas.
- NO debilitar bubblewrap ni los controles existentes.
- NO afirmar actividad que el runner no pueda observar.

## Acceptance criteria

1. Cada TASK tiene un comentario de estado identificable en su issue.
2. El mismo comentario se actualiza durante la ejecución.
3. Los estados visibles incluyen ESPERANDO, TRABAJANDO, VERIFICANDO, PUBLICANDO, TERMINÓ y FALLÓ.
4. Durante ejecución existe heartbeat periódico con duración/última actualización.
5. El estado final muestra commits, archivos, REPORT y rama cuando corresponda.
6. `VERIFY NOTHING` / cero commits no se presenta como implementación exitosa.
7. El workflow termina de forma no exitosa cuando una ejecución que debía producir implementación
   no entrega output publicable, con tests que demuestren el contrato.
8. Jobs relevantes escriben `GITHUB_STEP_SUMMARY`.
9. No se copian credenciales, variables protegidas ni contenido completo del agente al comentario.
10. Permisos nuevos, si existen, son mínimos y están documentados.
11. Tests cubren success, failure y NO_OUTPUT.
12. Los tests relevantes de aislamiento/protocolo existentes siguen pasando.
13. `git diff 6324b1f HEAD -- src/` está vacío.
14. Existe `reports/M05_REPORT.md`.
15. `docs/ai-development/CURRENT_STATE.md` queda actualizado.
16. Hay al menos un commit real de implementación.
17. Sin merge ni deploy.
18. REPORT explica exactamente cómo activar el cambio y cómo probarlo en la TASK siguiente.

## Evidencia requerida

- Lista exacta de archivos modificados.
- Tests ejecutados y resultados.
- Ejemplos renderizados de los seis estados.
- Evidencia de actualización del mismo comentario.
- Ejemplo de Step Summary.
- Evidencia del caso NO_OUTPUT.
- Permisos requeridos.
- Evidencia de que aislamiento y firebreak permanecen vigentes.
- `git diff 6324b1f HEAD -- src/`.
- REPORT y CURRENT_STATE.
- Commit y rama.
- Instrucción exacta para activar el cambio en la rama por defecto, sin efectuar merge.

## Decision gates

Preferir una solución GitHub-native pequeña sobre una reescritura del ejecutor.

Si para lograr el heartbeat fuese necesario reemplazar la arquitectura completa, agregar un
servicio externo, ampliar permisos de forma sustancial o reducir aislamiento, marcar
`DECISION_REQUIRED` y completar todo lo demás que no dependa de esa decisión.

La incorporación del cambio a la rama por defecto es `MERGE_GATE`: Claude implementa, ChatGPT
audita y Joaquín autoriza o rechaza.
