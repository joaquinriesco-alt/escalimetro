# E45.1 — Mobile upload hardening

## 1. Decisión aprobada
Joaquín aprobó endurecer el flujo de carga móvil de E45 antes del piloto real 20 MEJORAR + 20 CREAR. El objetivo es que material típico de iPhone no haga fallar o agote innecesariamente la web piloto. Es una corrección operacional de E45, no una nueva feature ni un cambio de producto.

## 2. Problema
La web E45 acepta CREAR sólo JPG/PNG/WEBP, mientras iPhone puede entregar HEIC/HEIF. Además, el POST actual lee todos los archivos completos a memoria antes de que las validaciones internas de CREAR limiten el lote. Una selección grande de fotos pesadas puede consumir memoria antes de rechazarla. MEJORAR sí tiene límite explícito por archivo; CREAR necesita límites claros, tempranos y mensajes humanos.

## 3. Contexto canónico
Base exacta: rama `e45_1_mobile_upload_hardening`, creada desde `auto/e45-issue-14` (E45 auditado PASS).

North Star: ESCALÍMETRO convierte planos en herramienta comercial. E45 es la web piloto para medir MEJORAR y CREAR. No alterar E44/E37 como sistemas de verdad salvo el mínimo necesario para aceptar/converter material móvil de forma segura.

Preservar:
- CREAR mantiene ground truth completamente oculto al motor hasta cierre/reveal.
- DEMO no cuenta en 20+20.
- E44 sigue siendo fuente de verdad de campaña.
- sin deploy, sin merge a main, sin cambios Railway.
- sin llamadas pagadas en tests.
- `src/` no debe modificarse.
- errores de archivo/lote nunca deben crear un caso parcialmente válido ni contaminar conteos.
- no exponer nombres originales innecesariamente al motor.

## 4. Resultado esperado
La web piloto funciona de manera robusta con cargas móviles típicas:
- CREAR acepta HEIC/HEIF de iPhone y los normaliza a un formato que el pipeline ya consume, sin hacer que el motor dependa de HEIC.
- Define y hace cumplir un máximo razonable de fotos por caso, tamaño máximo por foto y tamaño total del lote. Usa constantes/configuración explícitas y documenta los valores elegidos en el REPORT.
- Rechaza temprano archivos/lotes que exceden límites, antes de acumular innecesariamente todo el contenido en memoria.
- Valida también el plano real del modo piloto con límite razonable.
- MEJORAR conserva su límite y comportamiento existente.
- La UI móvil declara formatos/límites relevantes y devuelve mensajes comprensibles que identifican el problema sin jerga técnica.
- La conversión HEIC/HEIF conserva orientación visual correcta cuando la metadata disponible lo permita y produce JPG/PNG válido para el pipeline.
- Si la plataforma/librería necesaria para HEIC requiere una dependencia, agregar sólo la mínima dependencia reproducible compatible con Docker/Python 3.12; verificar build/import. No usar servicios externos.

## 5. No hacer
- No crear E46.
- No rediseñar la interfaz.
- No cambiar pricing, copy comercial, producto, layouts, motor de reconstrucción ni criterios arquitectónicos.
- No cambiar la lógica de ceguera/reveal.
- No agregar upload directo a S3 ni arquitectura nueva.
- No tocar Railway, deploy, main, workflows, executor o seguridad global.
- No hacer llamadas reales a OpenAI.
- No modificar `src/`.
- No convertir el piloto en un sistema de edición de fotos.
- No aceptar archivos sólo por extensión: mantener sniff/decodificación real.

## 6. Acceptance criteria
1. JPG/JPEG, PNG y WEBP siguen funcionando en CREAR.
2. HEIC y HEIF válidos subidos por CREAR son aceptados, decodificados y normalizados a formato soportado antes de entrar al proyecto E37.
3. Un archivo renombrado a .heic/.jpg sin contenido válido se rechaza.
4. Hay máximo explícito de cantidad de fotos CREAR, tamaño individual y tamaño total; todos tienen tests de borde/rechazo.
5. El rechazo por cantidad/peso/formato ocurre sin crear caso E44, proyecto E37, GT o eventos residuales.
6. El plano real de piloto tiene validación de tamaño y contenido y permanece oculto.
7. La ruta web no hace `read()` sin límite de todo el lote antes de validar límites; demostrar en código/tests que el límite se aplica durante la ingestión.
8. Mensajes web en español son accionables: archivo/lote demasiado grande, demasiadas fotos, formato no aceptado o archivo ilegible.
9. El selector móvil permite HEIC/HEIF además de formatos actuales cuando el navegador los expone.
10. Tests E45.1 pasan; correr además suite relevante E45+E44+E37 y reportar resultados exactos.
11. `git diff <base> HEAD -- src/ .github/ executor/` vacío.
12. No deploy, no merge main, no paid calls.
13. Si soporte HEIC reproducible no puede implementarse sin una dependencia riesgosa/incompatible, detenerse con DECISION_REQUIRED en vez de fingir soporte.

## 7. Evidencia requerida
Crear `reports/E45_1_REPORT.md` con PASS/PARTIAL/BLOCKED/DECISION_REQUIRED, archivos modificados, valores exactos de límites, estrategia HEIC/HEIF, dependencia si existe, cómo se evita cargar el lote entero sin límites, tests exactos y resultados, diff prohibido, limitaciones y recomendación para piloto.

Actualizar `reports/CURRENT_STATE.md` en el mismo commit final para dejar E45.1 como estado vigente si corresponde al protocolo.

Incluir tests automatizados para:
- HEIC/HEIF válido y corrupto;
- orientación cuando sea comprobable;
- límite de número;
- límite individual;
- límite total;
- GT demasiado grande/corrupto;
- lote rechazado deja 0 caso/proyecto/eventos;
- regresión JPG/PNG/WEBP;
- ceguera GT intacta;
- comportamiento de formulario/accept móvil.

No se requieren screenshots nuevas salvo que la UI cambie más que el texto/accept/límites.

- soporte HEIC exige una solución no reproducible o dependencia problemática;

- aparece una decisión de UX/producto más allá de mensajes de validación;
- se necesita Railway/deploy/secretos/pago;
- cualquier cambio excede hardening de upload.
