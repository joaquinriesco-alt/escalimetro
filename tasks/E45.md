# E45 — Web Piloto 40 Casos: probar producto + UX/UI

## Decisión aprobada

Joaquín decidió que **él mismo cargará y evaluará los 40 casos reales** de E44.

Por lo tanto, antes de ejecutar la muestra necesitamos una web usable que permita probar simultáneamente:

1. **calidad del producto** — MEJORAR PLANO y CREAR PLANO;
2. **calidad de la experiencia** — UX/UI, claridad, fricción, confianza y comprensión del resultado.

La web debe parecerse deliberadamente al producto que usaría un corredor, no a una consola técnica de benchmark.

North Star:
> **PLANOS QUE AYUDAN A VENDER.**

Core:
> **MEJORAR PLANO + CREAR PLANO.**

Joaquín será el primer usuario/tester. La campaña sigue siendo 20 MEJORAR + 20 CREAR. E45 construye la superficie para que pueda cargar esos casos y criticarlos. **E45 no inventa ni completa los 40 casos.**

## Problema

E44 dejó lista la infraestructura de campaña, pero sólo mediante CLI/import bundles. Eso sirve para trazabilidad, no para evaluar el producto como experiencia.

Si Joaquín carga los casos por scripts o una pantalla técnica, podremos medir el motor pero no responder:
- ¿se entiende qué hace Escalímetro?
- ¿se entiende la diferencia entre “tengo plano” y “no tengo plano”?
- ¿subir material es suficientemente simple?
- ¿la web pregunta demasiado?
- ¿el usuario confía en el resultado?
- ¿el resultado se presenta como herramienta comercial y no como software técnico?
- ¿CREAR PLANO comunica correctamente que es esquemático/referencial?
- ¿la experiencia funciona bien en desktop y móvil?

La UX deseada es optimista y automática: **preguntar sólo lo que no se pueda inferir con confianza**. Los detalles técnicos son internos.

## Resultado esperado

### A. Entrada: una decisión humana obvia

Crear una superficie piloto protegida para Joaquín, accesible desde web, cuyo primer paso sea visual y extremadamente simple:

**¿Qué necesitas hacer?**

**MEJORAR UN PLANO**
> Ya tengo un plano. Quiero dejarlo limpio y listo para publicar.

**CREAR UN PLANO**
> No tengo un plano útil. Quiero crear uno a partir de fotos e información de la propiedad.

No empezar con “motor”, “benchmark”, “caso”, “pipeline”, “ground truth” ni nombres técnicos.

La superficie de cliente debe mantener el lenguaje que eventualmente podría ver un corredor.

### B. Flujo MEJORAR PLANO

Camino principal:
1. elegir MEJORAR;
2. subir **un plano** (PDF/JPG/JPEG/PNG);
3. datos adicionales sólo si realmente son necesarios; no pedir programa, estilo, teléfono, empresa ni información irrelevante;
4. confirmar visualmente qué archivo se subió;
5. procesar por el camino real E44/E43 de MEJORAR;
6. si necesita revisión humana/técnica, mostrar al tester un estado comprensible, no jerga;
7. mostrar resultado con comparación visual **ANTES / DESPUÉS**;
8. permitir abrir/descargar el Plano Corporativo;
9. pasar a evaluación de Joaquín.

El plano original debe quedar asociado al caso E44 con provenance. No duplicar la lógica de campaña.

### C. Flujo CREAR PLANO

Camino principal:
1. elegir CREAR;
2. subir fotos de la propiedad, permitiendo múltiples imágenes;
3. permitir datos mínimos útiles: m² publicados y texto/link de referencia si Joaquín lo tiene. No exigir campos que el motor no necesita;
4. el **plano real/ground truth** se carga en un bloque claramente separado y sólo visible en **MODO PILOTO — NO SE ENVÍA AL MOTOR**;
5. antes de correr, UI debe dejar claro que ese plano real se usará únicamente para comparar al final;
6. ejecutar por E44/E37 con GT oculto;
7. mostrar reconstrucción sin revelar GT;
8. permitir corrección en lenguaje natural creando child run;
9. Joaquín pulsa explícitamente **CERRAR RECONSTRUCCIÓN Y COMPARAR**;
10. sólo entonces revelar GT;
11. mostrar **RECONSTRUCCIÓN / PLANO REAL** lado a lado;
12. pasar a evaluación.

Si falta credencial, la web debe mostrar un bloqueo accionable para el operador, sin fingir resultado ni romper el flujo.

### D. Panel de campaña para Joaquín

Ruta interna protegida, por ejemplo `/lab/campaign/e44/`, que muestre:

- progreso grande y simple: **MEJORAR 0/20** · **CREAR 0/20**;
- cards/listado de casos;
- estado humano comprensible:
  - NUEVO
  - MATERIAL CARGADO
  - PROCESANDO
  - NECESITA REVISIÓN
  - RESULTADO LISTO
  - EVALUADO
  - BLOQUEADO
- miniatura del input y output cuando existan;
- fecha;
- rating;
- botón **ABRIR CASO**;
- botón **NUEVO MEJORAR**;
- botón **NUEVO CREAR**.

Los N deben venir de E44; nunca inflarlos por uploads incompletos.

### E. Evaluación separada: PRODUCTO y EXPERIENCIA

Después de cada caso, Joaquín debe poder registrar dos juicios independientes.

**1. RESULTADO DEL PLANO**
- EXCELENTE
- BUENO
- MALO
- PESIMO
- comentario libre;
- ¿lo publicaría? sí/no;
- ¿necesitó corrección humana? sí/no;
- minutos humanos opcionales.

**2. UX / UI**
- EXCELENTE
- BUENO
- MALO
- PESIMO
- comentario libre;
- ¿entendí inmediatamente qué hacer? sí/no;
- ¿hubo una pregunta/paso que sobraba? comentario opcional;
- ¿hubo algo que faltaba? comentario opcional.

No score compuesto.

Guardar esta crítica en la campaña E44 como evidencia persistente. Debe ser posible volver al caso y editar/agregar una nueva evaluación con historial, no perder la anterior silenciosamente.

### F. Diseño

Esto es un test de UX/UI real.

Requisitos:
- desktop + móvil;
- mucho espacio blanco;
- tipografía/jerarquía sobria;
- imágenes/planos protagonistas;
- copy corto;
- botones y estados claros;
- no dashboard SaaS genérico;
- no tablas densas en el camino principal;
- before/after grande para MEJORAR;
- reconstrucción/GT grande para CREAR;
- feedback de Joaquín al final, no mezclado con la experiencia principal antes del resultado;
- privacidad visible y sobria: el material se usa para preparar/evaluar el plano;
- CREAR siempre rotulado como **esquemático/referencial** cuando corresponda.

Generar evidencia visual real de la UI con datos fixture **sólo para screenshots de UX**, claramente diferenciados de los casos E44 reales. Fixtures jamás cuentan en 20/20.

### G. Separación tester / cliente

La web puede tener controles especiales de piloto (GT, rating, feedback), pero deben estar visualmente separados del camino de cliente.

Ideal:
- **vista producto**: lo que sentiría/vería un corredor;
- **panel piloto**: progreso, GT, evaluación y crítica.

No contaminar el producto futuro con controles de benchmark.

## Acceptance criteria

1. Desde web protegida Joaquín puede iniciar MEJORAR o CREAR sin CLI.
2. La primera pantalla distingue ambos productos en lenguaje no técnico.
3. MEJORAR acepta un plano real y crea/actualiza correctamente un caso E44.
4. MEJORAR usa el pipeline real existente; no renderer fake.
5. Resultado MEJORAR muestra ANTES/DESPUÉS.
6. CREAR acepta múltiples fotos + metadata mínima.
7. GT de CREAR se carga separado, queda HIDDEN_FROM_ENGINE y la UI lo explica.
8. Blindness E44/E37 sigue protegida con tests adversariales.
9. CREAR permite run real, child correction y cierre blind.
10. GT sólo aparece tras cierre/reveal explícito.
11. Comparación CREAR muestra reconstrucción vs GT.
12. Panel muestra progreso honesto 0–20 por pista.
13. Casos incompletos no cuentan como completados.
14. Joaquín puede evaluar RESULTADO y UX/UI por separado.
15. Evaluaciones tienen historial/auditoría.
16. Estados/bloqueos son comprensibles sin jerga técnica.
17. Sin credencial, CREAR muestra bloqueo honesto y no fake success.
18. Desktop usable.
19. Móvil usable.
20. Screenshots de al menos:
    - elección MEJORAR/CREAR desktop;
    - upload MEJORAR;
    - before/after MEJORAR;
    - upload CREAR + GT separado;
    - reconstrucción pre-reveal;
    - comparación post-reveal;
    - evaluación resultado + UX;
    - panel 20/20;
    - al menos 3 vistas móviles representativas.
21. Fixtures de screenshots están marcados como DEMO y no alteran conteos E44.
22. Tests E44/E43/E37 relevantes siguen verdes.
23. Tests E45 cubren rutas, auth, upload, integración E44, blindness, reveal, evaluaciones, conteo honesto y responsive smoke.
24. `git diff 6324b1f HEAD -- src/` vacío.
25. REPORT + CURRENT_STATE.
26. Commit real posterior a TASK.
27. Sin merge/deploy/main.

## Decision gates

Emitir `DECISION_REQUIRED` sólo si:
- se necesita redefinir MEJORAR o CREAR;
- se propone pedir inputs adicionales de negocio no aprobados;
- se quiere decidir pricing/estilos/PRO;
- se quiere relajar blindness;
- se necesita tocar `src/`;
- se propone abrir Internet al executor;
- se necesita proveedor/modelo nuevo o gasto no aprobado;
- se quiere deploy/merge/main.

Detalles locales de layout, CSS, rutas internas y persistencia de feedback no requieren decisión si respetan este contrato.

**STOP esperado:** web piloto lista y probada en rama, con screenshots desktop/mobile y sin deploy.

**Después de E45:** ChatGPT audita y se detiene. Joaquín revisa screenshots/resultado y decide si quiere cambios de UX/UI o autorizar un deploy piloto para empezar a cargar los 40 casos. No crear E46 automáticamente.
