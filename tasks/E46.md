# E46 — Auditoría adversarial nocturna pre-piloto

## Decisión aprobada
Joaquín aprobó explícitamente una auditoría potente y prolongada para dejar corriendo durante la noche antes de probar casos reales mañana. E46 es AUDITORÍA, no desarrollo de producto. Debe consumir tiempo útil buscando fallos reales, no inventar features ni maquillar resultados.

## Problema
E45/E45.2 ya está desplegado como piloto, pero antes de ingresar material real necesitamos máxima confianza en que el sistema no pierde datos, no rompe ceguera, no acepta archivos peligrosos o falsos, no deja estados incoherentes y no tiene regresiones ocultas entre E37, E44, E45 y E45.2. Los tests existentes prueban caminos conocidos; esta auditoría debe buscar activamente caminos que no pensamos.

## Contexto canónico
Base exacta: auto/e45_2-issue-17. El producto sigue siendo ESCALÍMETRO: planos como herramienta comercial. Esta auditoría se hace contra el código del piloto actual. No hay acceso a Railway ni se deben asumir secretos o servicios externos. No hacer llamadas pagadas. No usar plano real como input del motor antes del reveal. Mantener DEMO fuera de métricas reales. No modificar src, .github ni executor. La auditoría puede crear tests/harnesses de auditoría y documentos de evidencia, pero NO corregir implementación productiva.

## Resultado esperado
Entregar una auditoría adversarial reproducible y priorizada de readiness para el piloto real. Dedicar el presupuesto disponible a inspección estática, trazado de estados, pruebas de integración, fuzz/boundary tests razonables y escenarios de fallo. Como mínimo cubrir: (A) integridad de E44 campaign/provenance/dedup/PII/counts; (B) ceguera CREAR antes del reveal, incluyendo filenames, SHA, rutas, manifests, HTML, logs/eventos y errores; (C) máquina de estados CREAR y MEJORAR y transiciones inválidas/repetidas; (D) uploads JPG/JPEG/PNG/WEBP/HEIC/HEIF/PDF, MIME/extensión/contenido, límites, decompression bombs, nombres extraños, path traversal, unicode y lotes; (E) persistencia/atomicidad ante excepciones simuladas y reintentos; (F) doble click/repetición/concurrencia razonable; (G) auth y same-origin de rutas piloto, acceso directo a artefactos y enumeración de IDs/tokens; (H) DEMO vs real y contaminación de métricas; (I) evaluaciones append-only, cierre/reveal y prohibición de corrección posterior; (J) compatibilidad móvil inferible desde HTML/backend; (K) dependencias/build/runtime Python 3.12 inferibles sin Docker; (L) regresión amplia del repo; (M) deuda que pueda bloquear mañana el primer caso real.

Para cada hallazgo: severidad BLOCKER/HIGH/MEDIUM/LOW, evidencia reproducible, impacto concreto, alcance afectado, si ya existe test que lo detecta, y corrección mínima sugerida SIN implementarla. Separar claramente defecto demostrado, riesgo plausible no reproducido y limitación conocida. Buscar contradicciones entre TASKs, REPORTs, CURRENT_STATE y código. No declarar PASS por ausencia de evidencia.

Ejecutar la suite completa si cabe dentro del presupuesto temporal y registrar duración/resultados exactos. Además, diseñar y ejecutar tests adversariales nuevos donde aporten evidencia. Priorizar profundidad sobre cantidad superficial. Si un test tarda mucho, registrar por qué. No usar red ni APIs pagadas.

## No hacer
No arreglar bugs productivos. No cambiar webapp productivo, src, requirements, Dockerfile, Railway, .github, executor, pricing, copy comercial, UX, motor, E37/E44 doctrine ni datos reales. No deploy, merge, PR ni main. No agregar features. No hacer llamadas OpenAI/Anthropic desde el producto. No falsificar pruebas de navegador/iPhone/Railway que el sandbox no pueda realizar. No rebajar severidades para obtener PASS. No convertir recomendaciones en implementación. Sólo se permiten archivos de auditoría bajo tests/ y reports/ y la actualización protocolaria de docs/ai-development/CURRENT_STATE.md si corresponde.

## Acceptance criteria
1. Existe reports/E46_REPORT.md con veredicto final READY / READY_WITH_FINDINGS / NOT_READY, sustentado por evidencia.
2. Existe matriz de cobertura con todos los dominios A–M y resultado probado/no probado/hallazgo.
3. Cada BLOCKER/HIGH tiene reproducción concreta o queda marcado explícitamente como riesgo no reproducido.
4. Se ejecuta la suite completa del repo si el tiempo lo permite; si no, se registra exactamente qué quedó fuera.
5. Se ejecutan suites E37+E44+E45+E45.2 y tests adversariales E46.
6. Se audita explícitamente que GT no filtre antes de reveal por ninguna superficie observable en repo/tests.
7. Se prueban transiciones repetidas, requests duplicados y fallos simulados en puntos críticos de persistencia.
8. Se prueban inputs hostiles razonables sin convertir esto en pentest destructivo.
9. Se revisan rutas auth/origin/artifacts y exposición accidental de información.
10. Se revisa que DEMO no contamine 20+20 ni evaluaciones reales.
11. Se revisan dependencias y compatibilidad de pillow-heif/Python 3.12 hasta donde permite el sandbox.
12. git diff de la implementación final contra la TASK no contiene cambios productivos; sólo evidencia/tests/CURRENT_STATE.
13. El REPORT termina con una lista priorizada: MUST FIX BEFORE FIRST REAL CASE / FIX DURING PILOT / ACCEPT FOR PILOT.
14. Si aparece un defecto crítico, NO corregirlo: documentarlo con reproducción y marcar NOT_READY.
15. CURRENT_STATE queda actualizado con el resultado de E46 y la base exacta para una eventual próxima TASK, sin inventar una E47.

## Evidencia requerida
Crear reports/E46_REPORT.md. Incluir commit/base, metodología, tiempo aproximado invertido por fase, comandos ejecutados, resultados exactos de tests, matriz A–M, hallazgos numerados con severidad y reproducción, invariantes confirmados, invariantes rotos, áreas no observables, falsos positivos descartados, deuda previa distinguida de regresiones nuevas y recomendación de readiness. Los tests nuevos de auditoría deben quedar bajo tests/ con nombres E46 y deben probar comportamiento actual, no imponer features nuevas. Actualizar docs/ai-development/CURRENT_STATE.md en el mismo commit final según protocolo. Verificar diff prohibido de src/, .github/, executor/, webapp/, requirements.txt, Dockerfile y cualquier archivo productivo: debe ser vacío respecto de la TASK commit. Registrar explícitamente que no hubo deploy/merge/paid calls.

## Decision gates
Si para demostrar un hallazgo hace falta modificar código productivo, detener esa línea y documentar el límite; no modificarlo. Si aparece exposición de secretos, corrupción de datos, bypass de auth, fuga del GT o riesgo de llamadas pagadas involuntarias, elevar a BLOCKER y continuar auditando otras áreas sin explotar datos reales. Si el sandbox no permite comprobar Railway/iPhone/browser real, marcarlo NO PROBADO, no inferir PASS. E46 no autoriza ninguna corrección ni siguiente TASK.
