# E43 — Plano Corporativo revisable + enlace de entrega

## Decisión aprobada

Completar el primer circuito concierge vendible de **Plano Corporativo** sin precio ni pago:

> pedido público → propiedad interna → preparación/revisión humana → Plano Corporativo → enlace público opaco de entrega.

El cliente ya subió email + plano en E41 y E42 lo convirtió en una propiedad del LAB. E43 debe reutilizar la salida existente `floorplan.publish_commercial_floorplan` / `commercial_svg`, pero **nunca publicar una geometría no confirmada**.

La entrega inicial será mediante un enlace público opaco que el operador puede copiar y enviar manualmente. E43 **no envía email**. Esto evita decidir infraestructura externa y mantiene el concierge.

La revisión humana sigue siendo compuerta: generar/ver un candidato internamente no equivale a publicarlo al cliente.

## Problema

Hoy E42 deja el pedido dentro del LAB, pero todavía no existe un circuito mínimo y seguro para:
1. saber si la geometría está lista;
2. generar/ver el Plano Corporativo existente;
3. aprobar explícitamente esa pieza;
4. obtener un enlace público que exponga sólo el entregable aprobado de ese pedido.

Sin esto, el primer producto todavía no cierra de punta a punta.

## Resultado esperado

### A. Operación interna

1. Desde el pedido preparado / propiedad del LAB, el operador puede distinguir claramente:
   - planta aún no lista / requiere revisión;
   - planta lista para producir Plano Corporativo;
   - candidato de Plano Corporativo generado;
   - Plano Corporativo aprobado y enlace listo.
2. Si la geometría no está lista según las compuertas existentes, no se genera ni publica el Plano Corporativo. Se conserva el camino actual del LAB para preparar/revisar la planta.
3. Cuando la geometría ya está lista, una acción interna protegida puede generar/regenerar el candidato usando **exactamente** la salida existente `floorplan.publish_commercial_floorplan`.
4. El candidato se ve internamente antes de publicar.
5. Una acción POST separada y explícita **APROBAR PARA ENTREGA** (o redacción equivalente) fija qué asset `FLOORPLAN_COMMERCIAL` queda aprobado para ese pedido.
6. Regenerar un candidato no debe cambiar silenciosamente el entregable ya aprobado. Si técnicamente conviene invalidar la aprobación al regenerar, debe quedar explícito y testeado; nunca sustituir en silencio el asset detrás de un link aprobado.

### B. Entrega pública mínima

7. Al aprobar, crear/persistir un token opaco, no secuencial y suficientemente largo, asociado al pedido y al asset aprobado.
8. Crear una ruta pública mínima bajo `/planos/` que, dado ese token:
   - muestre una página sobria de “Plano Corporativo listo”;
   - permita ver/descargar **sólo** el asset aprobado;
   - no exponga email, property_id, request_id, filesystem path, herramientas internas ni otros assets.
9. Token inexistente/malformado → 404.
10. Un token de un pedido nunca puede servir un asset de otra propiedad/pedido.
11. La página pública no requiere HTTP Basic; toda generación, aprobación, listado y administración sí lo requieren.
12. El operador puede copiar el enlace desde la bandeja/pedido interno. No enviar email automáticamente.
13. Persistir un estado honesto del pedido, por ejemplo `READY_FOR_DELIVERY`, al aprobar. No llamarlo `DELIVERED` porque E43 no prueba que el cliente haya recibido el enlace.

### C. Seguridad y alcance

14. La ruta pública sirve el archivo a través de la capa/validación de assets existente o una barrera equivalente por asset + propiedad; nunca acepta paths del usuario.
15. No ejecutar automáticamente el motor, layouts, staging ni red al abrir el link o aprobar.
16. Generar el plano comercial puede usar el shell ya confirmado y CairoSVG existente; no debe relajar readiness ni confirmaciones.
17. El formulario E41 y la preparación E42 siguen funcionando.

## Acceptance criteria

1. Pedido E42 preparado conserva su vínculo a propiedad.
2. Sin geometría ready, generar candidato falla de forma controlada y no crea token/entrega.
3. Con geometría ready, la acción interna usa `publish_commercial_floorplan` y crea un único candidato actual.
4. El candidato puede previsualizarse internamente con HTTP Basic.
5. Ningún link público existe antes de aprobación explícita.
6. Aprobar persiste asset aprobado + token opaco + timestamp + estado `READY_FOR_DELIVERY` o equivalente honesto.
7. La ruta pública por token responde 200 sin auth y muestra/descarga sólo el plano aprobado.
8. No expone email, IDs internos, paths ni navegación interna.
9. Token inválido/desconocido responde 404.
10. Cross-property/cross-request asset access está impedido y testeado.
11. Repetir aprobación es idempotente o rota token de manera explícita y segura; nunca crea estados ambiguos.
12. Regenerar candidato no sustituye silenciosamente el asset ya aprobado detrás de un token existente.
13. Abrir/refrescar el enlace no cambia estado a DELIVERED ni produce efectos.
14. Generación/aprobación/link no abren red ni ejecutan layouts/staging/proveedores.
15. E40/E41/E42 y LAB relevante siguen verdes.
16. Tests nuevos cubren readiness, generación, preview interna, aprobación, token, 404, aislamiento, idempotencia y no exposición de PII.
17. `git diff 6324b1f HEAD -- src/` vacío.
18. `reports/E43_REPORT.md` + `CURRENT_STATE.md` actualizados.
19. Al menos un commit real posterior a la TASK.
20. Sin merge, deploy ni movimiento de `main`.
