# E47.8 — H05/H20: reintento CREAR + exclusión que libera la propiedad

## Decisión aprobada

Joaquín aprobó continuar con H05/H20 después de auditar E47.7.

La semántica ya decidida es:

- un fallo técnico de CREAR puede reintentarse;
- cada intento debe quedar registrado;
- un intento técnico fallido NO consume uno de los 20 casos válidos;
- cuando finalmente existe un resultado válido, ese caso cuenta una sola vez;
- excluir un caso debe liberar esa propiedad/material para poder cargarla de nuevo;
- no se cambia producto, pricing, motor, ni la definición de calidad del resultado.

## Problema

E46-H05 demostró que una corrida inicial CREAR que termina FAILED queda definitiva: el caso pasa a una condición sin salida, start_create ya no puede arrancar otra corrida y la web no ofrece un reintento utilizable.

E46-H20 demostró que incluso después de excluir el caso, _find_duplicate sigue considerando ese caso y bloquea volver a cargar la misma propiedad/material.

Además, el modelo actual tiene varias suposiciones de “una sola corrida inicial” que deben revisarse de forma coherente:

- pipeline es tratado como singleton;
- status() considera cualquier pipeline como EXECUTED aunque sea FAILED;
- count()/summary() pueden terminar consumiendo un caso fallido dentro de la métrica del piloto;
- start_create() bloquea al existir cualquier create_started;
- settle() debe seguir siendo idempotente si existen varios intentos;
- el case_id puede ser determinista, por lo que liberar duplicados tras exclusión no debe provocar colisiones ni mezclar evidencia de dos casos.

## Acceptance criteria

1. Un CREAR cuyo primer intento inicial termina FAILED puede lanzar un segundo intento desde la misma web/caso.
2. El intento anterior permanece registrado e inmutable; el nuevo intento tiene identidad/orden distinguible.
3. Un caso con 1 o más intentos iniciales FAILED y ningún DONE:
   - no cuenta como executed;
   - no cuenta como completed;
   - no consume uno de los 20 válidos.
4. Si un intento posterior termina DONE:
   - el caso cuenta exactamente una vez como executed;
   - las fallas anteriores siguen en historial;
   - no se permite otra corrida inicial adicional.
5. No se permite reintento si:
   - existe una corrida inicial pendiente;
   - hay cierre/reveal/evaluación;
   - ya existe un intento inicial DONE.
6. Doble clic/concurrencia durante un reintento crea como máximo una corrida nueva y conserva H03.
7. settle() puede ejecutarse repetidamente y tras reinicio sin duplicar eventos ni cambiar conteos.
8. BLOCKED_CRED sigue recuperable como antes y no se confunde con un intento FAILED.
9. Las correcciones posteriores a un DONE siguen funcionando y no se mezclan con los intentos iniciales.
10. Excluir un caso hace que _find_duplicate deje de bloquear esa misma propiedad/material.
11. Volver a cargar una propiedad excluida crea un caso nuevo con:
    - case_id distinto;
    - carpeta/evidencia distinta;
    - resultados/eventos distintos;
    - proyecto de reconstrucción distinto cuando aplique.
12. El caso excluido permanece intacto y sigue apareciendo como EXCLUDED con su motivo.
13. Los casos activos no excluidos siguen deduplicando igual dentro y entre pistas.
14. Los tests que reproducían E46 H05 (E6, E6b, E7) y H20 (A9) quedan verdes o se reemplazan por assertions equivalentes explícitas.
15. Añadir tests focales que prueben al menos:

    - FAILED nunca cuenta en N;
    - retry concurrente/doble envío;
    - exclude → reupload con identidad separada;
    - settle idempotente con varios intentos.
16. Ejecutar suites focales E44/E45/E46/E47 relevantes, especialmente H01/H02/H03/H10/H16, sin regresiones atribuibles a esta TASK.
