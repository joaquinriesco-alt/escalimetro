# E47.10 — H21: errores de proveedor no rompen settle ni el panel

## Decisión aprobada

Joaquín aprobó continuar con H21 después de cerrar y auditar H01, H02, H03, H05, H10, H16 y H20.

Esta TASK corrige exclusivamente E46-H21.

Semántica a preservar:

- los textos escritos por personas siguen sujetos a la protección de PII vigente;
- un error técnico generado por el sistema, motor o proveedor debe poder registrarse de forma segura sin convertir una lectura del caso/panel en 500;
- el error persistido no debe exponer secretos, credenciales, emails, teléfonos, rutas sensibles ni identificadores largos innecesarios;
- en CREAR, un fallo técnico sigue siendo reintentable y no consume uno de los 20 casos válidos, según E47.8/E47.9;
- en MEJORAR, no se cambia la semántica del flujo salvo evitar que el registro del error rompa la operación;
- no se cambia producto, UX estratégica, métricas, motor ni proveedor.

## Problema

E46-H21 demostró que `record()` aplica `_no_pii` al campo `error` porque `error` está dentro de `_FREE_TEXT`. Un mensaje técnico puede contener una secuencia numérica de 9+ dígitos, un request id, timestamp, ticket, ruta temporal u otro texto que el detector interpreta como teléfono/PII.

Consecuencia demostrada:

- una corrida CREAR puede terminar FAILED correctamente en E37;
- `settle()` intenta convertirla en evento `pipeline`;
- `_check_payload()` → `_no_pii()` rechaza el texto técnico del error;
- `CampaignError` se propaga desde `settle()`;
- la página del caso y `/panel` pueden responder 500;
- el caso queda artificialmente PROCESANDO porque el FAILED nunca se asienta;
- el mismo patrón afecta MEJORAR cuando `improve_started` intenta persistir un error técnico;
- en E46 se reprodujo con `1700000000`, `ticket 123-456-7890` y errores con ids/rutas numéricas.

Esto es un error de frontera de confianza: un detector diseñado para texto humano está rechazando texto generado por el propio sistema.

## Resultado esperado

Cerrar H21 de forma mínima y segura.

1. Separar explícitamente el tratamiento de texto **humano/no confiable** del texto **técnico generado por sistema/proveedor**.
2. Mantener `_no_pii` (o protección equivalente) para todos los campos que una persona puede escribir: comentarios, prompts/correcciones, motivos, notas u otros campos humanos vigentes.
3. Antes de persistir un error técnico, convertirlo a una representación segura y acotada que conserve utilidad operativa sin exponer datos sensibles. Es aceptable conservar, por ejemplo, tipo/código de error y una descripción sanitizada/truncada.
4. La sanitización debe ser determinista y debe cubrir al menos:
   - secuencias de 9+ dígitos y números con separadores;
   - emails;
   - teléfonos;
   - rutas temporales/locales sensibles;
   - tokens/keys evidentes si aparecieran;
   - textos excesivamente largos.
5. No eliminar la protección PII global como atajo. No permitir que un campo humano pase sin validar por el solo hecho de llamarse `error` o `detail`.
6. `settle()` debe ser fail-safe respecto del contenido del error: una corrida DONE/FAILED válida debe poder asentarse y el panel debe seguir respondiendo aunque el mensaje bruto del proveedor sea hostil para el detector.
7. CREAR: un FAILED con error hostil debe quedar asentado como FAILED seguro, status reintentable según E47.8/E47.9 y sin contar como executed/completed.
8. MEJORAR: un error técnico equivalente debe poder registrarse sin 409/500 por PII técnica y sin dejar una propiedad huérfana por fallo del registro.
9. Si el sistema no puede sanitizar con confianza un texto, debe guardar un mensaje genérico seguro + clase/código de error; nunca propagar el texto bruto para romper la página.
10. El panel/caso debe mostrar un mensaje útil pero seguro; no hace falta rediseñar UX.

## Acceptance criteria

1. Reproducir el H21 original con un error de proveedor que contenga `1700000000` y demostrar que:
   - `settle()` no lanza `CampaignError`;
   - el caso no queda falsamente PROCESANDO;
   - GET del caso responde 200;
   - GET `/panel` responde 200.
2. Repetir con al menos:
   - `ticket 123-456-7890`;
   - un email sintético;
   - una ruta/identificador largo con dígitos;
   - un texto exageradamente largo.
3. El evento persistido no contiene literalmente los valores sensibles/hostiles usados en los tests cuando corresponda sanitizarlos.
4. El evento mantiene información operativa suficiente: al menos status/clase y un error seguro o código equivalente.
5. CREAR FAILED con error hostil:
   - queda asentado;
   - sigue CAPTURED/reintentable;
   - `executed == 0` y `completed == 0`;
   - el siguiente retry legítimo funciona;
   - no se crea una corrida extra por el simple GET/settle.
6. CREAR DONE no cambia: sigue asentando correctamente y E47.9 continúa impidiendo reintento después de DONE.
7. MEJORAR con excepción técnica cuyo texto contiene una secuencia que parece PII:
   - no produce 409/500 por el detector;
   - registra un estado/error seguro;
   - no crea una propiedad huérfana por fallo de `record` atribuible a ese texto.
8. Un comentario/prompt humano con email o teléfono sigue siendo rechazado por la protección PII existente.
9. `settle()` sigue siendo idempotente después de un FAILED hostil: múltiples GET no duplican eventos ni cambian conteos.
10. El panel con varios casos no cae porque uno contenga un error técnico hostil.
11. Los tests originales E46 H21 (`E11`, `E11b`, `E11c`, o equivalentes explícitos) pasan como regresión cerrada.
12. Suites focales de E45/E46/E47 pasan, especialmente H01/H02/H03/H05/H10/H16/H20 y E47.9.
13. Cero llamadas pagadas.
14. `reports/E47.10_REPORT.md` y `docs/ai-development/CURRENT_STATE.md` quedan actualizados en el mismo commit.
15. El REPORT declara H21 PASS/PARTIAL/BLOCKED con evidencia concreta. Si PASS, debe indicar que los HIGH/BLOCKER priorizados de E46 quedan cerrados y que el siguiente paso es E48 final readiness audit, no deploy automático.
