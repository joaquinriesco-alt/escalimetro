# M01 — Handoff ChatGPT ↔ Claude a través del repo

## Decisión aprobada

Joaquín + ChatGPT, 2026-09-29: dejar de usar a Joaquín como transporte manual de prompts y
reportes entre ChatGPT y Claude Code, **sin** quitarle autoridad de producto. El repo pasa a ser la
memoria operacional y el canal persistente. En la misma entrega se fija la doctrina vigente: el
core es CREAR PLANO y MEJORAR PLANO.

Fuente original: `ESCALIMETRO_M01_AI_DEVELOPMENT_HANDOFF.md` (1.050 líneas, entregado por Joaquín
fuera del repo). Esta TASK es su versión persistida.

## Problema

```
Joaquín + ChatGPT → Joaquín copia el prompt → Claude construye → Joaquín copia el reporte
→ ChatGPT audita → Joaquín copia el siguiente prompt → …
```

Los prompts rondan las 500–1.000 líneas y los reportes, miles de palabras. Nada de eso queda en el
repo: si se pierde la conversación, se pierde el contexto.

## Resultado esperado

Un agente competente que abra el repo sin historial de conversación puede responder: qué es
ESCALÍMETRO hoy, cuál es el core, qué está construido y qué congelado, qué experimentos siguen
activos, cuál fue la última tarea, qué cambió, qué tests pasaron, qué evidencia hay, qué decisiones
requiere Joaquín, qué hace Claude después y qué **no** está autorizado a decidir.

## No hacer

- No modificar funcionalidad de ESCALÍMETRO (`webapp/`, `src/`).
- No construir el Reconstruction Lab (va como TASK aparte).
- No agentes 24/7, auto-merge, auto-deploy, bus de mensajes, dashboards ni infraestructura cloud.
- No merge a `main`. No deploy.
- No inventar hechos ni reescribir historia técnica no verificada.
- No crear documentos que no eliminen trabajo manual real.

## Acceptance criteria

1. Existe una doctrina persistida con el core CREAR / MEJORAR PLANO y los roles.
2. Existe un `CURRENT_STATE.md` verificado, legible en menos de dos minutos.
3. Existe un protocolo con formatos de TASK, REPORT y `DECISION_REQUIRED`.
4. Existe un registro de decisiones duraderas con procedencia citada.
5. Claude Code recibe la doctrina y el protocolo **sin que nadie los pegue** al abrir el repo.
6. Esta TASK queda representada en `tasks/`, con su REPORT en `reports/`.
7. Un agente sin historial reconstruye el estado del proyecto leyendo sólo el repo.
8. Las decisiones pendientes quedan explícitas.
9. Un test impide que el sistema se desincronice (una TASK sin REPORT, un enlace roto).
10. La suite existente no regresiona.

## Evidencia requerida

Suite completa antes y después; transcripción de la reconstrucción por un agente sin historial;
listado de archivos; commit y rama.

## Decision gates

Detenerse con `DECISION_REQUIRED` ante: la topología de ramas y qué es `main`; la visibilidad
pública del repo; el futuro de `/property` y del scoring de E17 bajo la nueva doctrina; cualquier
cambio de doctrina más allá de persistir la que se entregó.

## Fuente

Lo que las decisiones D-001 a D-004 y D-009 citan, persistido acá para que la cita resuelva
dentro del repo. **Resumen redactado por Claude** a partir del documento original entregado por
Joaquín (`ESCALIMETRO_M01_AI_DEVELOPMENT_HANDOFF.md`, fuera del repo). Si difiere del original,
manda el original.

**Autoridad.** Joaquín es product owner y autoridad final: decide qué es ESCALÍMETRO, el problema,
para quién, prioridades, pricing, UX relevante, experimentos, qué congelar o eliminar, qué es
calidad suficiente, cuándo algo está listo, cuándo cambiar de dirección, vender o desplegar.

**ChatGPT** trabaja con Joaquín como product lead, arquitecto conceptual, diseñador de
experimentos y de acceptance gates, auditor independiente y crítico. No implementa el repo.

**Claude Code** implementa: inspecciona antes de actuar, ejecuta TASKs aprobadas, escribe código y
tests, corre experimentos, guarda evidencia, documenta. Decide lo técnico local. No decide cambiar
el core, convertir una aplicación en producto, pricing, UX estratégica, otra vertical, redefinir
CREAR o MEJORAR PLANO, poner PRO / layouts / staging / video en el centro, relajar fidelidad,
inventar doctrina, ocultar fallos, ni empezar sola una fase grande. Ante eso: `DECISION_REQUIRED`.

**Doctrina.** Core 1 CREAR PLANO (no tienes → lo inferimos; inputs posibles: URL o publicación,
fotos, video, superficie, dirección y contexto, descripción, antecedentes públicos verificables;
salida: Plano Esquemático Comercial, referencial, comercial, trazable, honesto sobre incertidumbre,
corregible por lenguaje natural y nunca presentado como levantamiento arquitectónico). Además:
corrección humana por prompts, no CAD; nunca fingir certeza geométrica; producto 100 % remoto como
dirección, sin depender de visita física. *Completado en M01.1: la primera versión de este resumen
omitía estas líneas, que `PRODUCT_DOCTRINE.md` sí recoge.* Core 2 MEJORAR PLANO (ya tienes → Plano Comercial
publicable, tendiendo a muy automático y barato). Meta 90 % IA / 10 % humano, medible, no claim.
Todo lo demás —cabida, layouts, PRO, test-fit, staging, renders, video, reels, scoring de
publicaciones— es aplicación o infraestructura.

**Gates.** PRODUCT_GATE, EXPERIMENT_GATE, MERGE_GATE (sin auto-merge), DEPLOY_GATE (sin deploy por
completar una tarea), DIRECTION_GATE (Claude detecta oportunidades, no redefine el producto).

**No construir ahora.** Agente 24/7, auto-merge, auto-deploy, framework multiagente, bus de
mensajes, base vectorial de conversaciones, dashboard de agentes, microservicios, infraestructura
cloud, permisos complejos.

**Iniciativa aprobada, fuera de M01: Internal Reconstruction Lab.**

```
Proyecto → inputs → Motor A / B / C → corrida inmutable → resultado
→ corrección por prompt → corrida hija → calificación → historial
→ reveal del ground truth → comparación
```

Experimentos que el documento cita como ejemplo: benchmark histórico de 34 fotos → plano; Motor A
vs B vs C; máximo 3 prompts humanos; ground truth oculto; 10 propiedades; calidad
Excelente / Bueno / Malo / Pésimo. M01 no lo construye: debe entregarse como TASK separada.
