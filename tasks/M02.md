# M02 — GitHub-native Claude executor

## Decisión aprobada

Joaquín + ChatGPT, 2026-09-30: eliminar el último transporte manual del ciclo de desarrollo de
ESCALÍMETRO. Hoy ChatGPT ya escribe la TASK en GitHub y audita el resultado desde GitHub, pero
Joaquín todavía tiene que abrir Claude Code y escribir «Ejecuta <ID>».

M02 debe dejar preparado un ejecutor GitHub-native para que, una vez activado de forma segura, el
flujo normal sea:

```
Joaquín + ChatGPT aprueban una TASK
        ↓
ChatGPT crea rama + tasks/<ID>.md
        ↓
ChatGPT crea un issue de transporte con ID + rama + commit
        ↓
GitHub Actions invoca Claude Code
        ↓
Claude verifica la TASK, implementa, prueba, REPORT + STATE y push
        ↓
ChatGPT lee GitHub y audita
        ↓
Joaquín decide
```

La automatización es **del transporte y la ejecución de una TASK ya aprobada**, no del juicio.
Joaquín sigue siendo la autoridad final. ChatGPT sigue diseñando/auditando. Claude sigue
implementando. No hay auto-merge, auto-deploy ni autonomía para inventar la siguiente TASK.

Esta aprobación amplía la superficie de transporte de ChatGPT de D-010: además de crear la rama y
`tasks/<ID>.md`, ChatGPT podrá crear el **issue de ejecución** estrictamente mecánico que referencia
esa TASK. Claude debe persistir esta ampliación como una decisión nueva sólo si la implementación
resulta viable y sus límites quedan verificables.

## Problema

M01/M01.1 resolvieron el copy/paste y E37 demostró el primer ciclo real
ChatGPT → GitHub → Claude → GitHub → ChatGPT. Queda una manualidad: Joaquín tiene que abrir Claude
y nombrar la TASK. Eso no agrega criterio ni control; sólo transporta un ID.

No queremos reemplazar esa manualidad por un «agente autónomo» genérico. Queremos un mecanismo
mínimo, auditable y revocable que ejecute **exactamente una TASK aprobada** y nada más.

## Contrato de transporte

Diseña un formato pequeño, parseable y versionado. Como mínimo el issue debe transportar:

```
ESCALIMETRO_AUTO_TASK_V1
TASK_ID=<Mxx o Exx[.n]>
TASK_BRANCH=<rama creada por ChatGPT>
TASK_COMMIT=<SHA exacto del commit que agregó tasks/<ID>.md>
BASE_BRANCH=<base declarada por CURRENT_STATE al crear la TASK>
TASK_PATH=tasks/<ID>.md
```

No confiar en texto libre del issue para definir producto ni implementación. El contenido
autoritativo es `tasks/<ID>.md` en `TASK_COMMIT`.

El preflight debe fallar cerrado si, como mínimo:

- el actor del evento no es el usuario autorizado del repo;
- falta o sobra una clave crítica del contrato;
- el ID/rama/path no cumplen formato seguro;
- `TASK_COMMIT` no es el HEAD esperado de `TASK_BRANCH`;
- `BASE_BRANCH` no existe;
- la rama no desciende de la base;
- el diff base → TASK_COMMIT no es **sólo** `tasks/<ID>.md`;
- el archivo no existe en ese commit;
- la TASK no declara «Decisión aprobada»;
- la TASK ya tiene REPORT cerrado o existe evidencia inequívoca de ejecución previa;
- la rama o commit cambió entre la creación del issue y el preflight.

El issue no otorga permiso para merge, deploy, cambios de doctrina ni una TASK posterior.

## Diseño de ramas

La action oficial, al ejecutarse desde un issue, crea una rama nueva. Aprovecharlo en vez de pelear
contra el mecanismo:

```
<base anterior>
   └─ <task_branch>          ← ChatGPT; sólo tasks/<ID>.md
        └─ <claude_branch>   ← Claude Code Action; implementación + tests + REPORT + STATE
```

El executor debe pasar `TASK_BRANCH` como `base_branch` de Claude Code Action después del
preflight. La rama de Claude tiene que poder relacionarse inequívocamente con el issue/TASK.
No mergear automáticamente la rama hija a la rama de TASK ni a `main`.

Al cerrar, `CURRENT_STATE.md` debe declarar la **rama de implementación de Claude** como base para
la próxima TASK si M02 pasó.

El repo público hace estas compuertas obligatorias. Si Claude concluye que no puede hacer esto de

- construye y prueba el workflow en su rama;
- verifica por GitHub la rama default actual;
- verifica si puede observar el estado de protección de `main`;
- registra que Joaquín informó que deshabilitó Auto Deploy del backend de Railway, pero no lo
  presenta como verificación API si no puede comprobarlo;
- **NO** mergea ni copia el workflow a `main`;
- **NO** cambia default branch;
- **NO** reactiva Railway;
- termina con una propuesta de activación mínima después de la auditoría de ChatGPT.

Si activar exige resolver DR-1/DR-8, eso es `DECISION_REQUIRED`, no una excusa para saltarse el
gate.
