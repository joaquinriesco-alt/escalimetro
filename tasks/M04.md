# M04 — Claude Live: progreso observable del ejecutor

## Decisión aprobada

Joaquín aprobó incorporar **Claude Live** al circuito GitHub-native de ESCALÍMETRO antes de seguir
acumulando TASKs de producto.

Objetivo:

> **Automático, pero visible.**

Joaquín debe poder abrir la ejecución o el issue cuando quiera y saber si el sistema está esperando,
preparando, ejecutando Claude, verificando, publicando, terminó o falló. Mirar debe ser opcional:
el circuito sigue funcionando sin que Joaquín tenga la ventana abierta.

Claude Live muestra **actividad operacional observable**, nunca razonamiento interno ni
chain-of-thought.

El formato deseado es conceptualmente:

```
E41 — EN EJECUCIÓN
✅ TASK validada
✅ Runner / aislamiento listo
🔄 Claude implementando · 08 min
○ Verificación
○ Publicación
○ Auditoría ChatGPT
```

y al terminar:

```
E41 — CLAUDE TERMINÓ
✅ TASK validada
✅ Aislamiento
✅ Claude
✅ commits / archivos
✅ Verificación
✅ Rama publicada
○ Auditoría ChatGPT
```

No tiene que ser literalmente ese diseño si GitHub impone otra representación, pero debe entregar
esa información con claridad.

## Problema

El ejecutor actual funciona, pero durante el paso `Claude ejecuta la TASK` la acción oculta el
output completo por seguridad. Desde afuera sólo se ve una caja larga “in progress”. En E40,
Joaquín no pudo distinguir entre “Claude está trabajando” y “el sistema quedó detenido”.

Además:
- E38 demostró que un workflow verde puede ocultar `VERIFY NOTHING`.
- Las notificaciones de término pueden llegar a la app de ChatGPT, pero no actualizan mágicamente
  una conversación ya abierta.
- El problema de esta TASK NO es exponer el razonamiento de Claude. Es exponer el **estado del
  proceso**.

GitHub Actions soporta logs, estados de jobs y `GITHUB_STEP_SUMMARY`; el repo además ya comenta el
resultado final en el issue. Hay que convertir esas piezas en una superficie de progreso legible.

## Resultado esperado

Implementar **Claude Live v1** en el ejecutor con una superficie observable y segura.

### A. Un único estado vivo por TASK

El issue de transporte debe tener un bloque/comentario identificable de Claude Live que pueda
actualizarse sin generar spam. Preferir **actualizar un mismo comentario** en vez de crear uno nuevo
cada minuto.

Debe mostrar como mínimo:
- TASK ID;
- estado global legible;
- etapa actual;
- hora de inicio;
- tiempo transcurrido o heartbeat reciente mientras Claude corre;
- link al run;
- estados de gate, Claude, verificación y publicación;
- al final: commits, archivos cambiados, REPORT sí/no, rama publicada o motivo de fallo;
- “Auditoría ChatGPT: pendiente” hasta que exista auditoría externa.

### B. Heartbeat durante Claude

Mientras el job de Claude está realmente `queued` o `in_progress`, Claude Live debe refrescarse
periódicamente con una cadencia razonable (objetivo: alrededor de 60 s; puede ser algo mayor si
reduce complejidad).

No afirmar “editando archivo X” o “corriendo test Y” si el workflow no puede observarlo realmente.

Un heartbeat válido es:

`Claude implementando · 8 min · última señal 20:14`

porque eso es observable desde el estado del job.

Si técnicamente es seguro obtener más granularidad observable sin revelar output oculto
(p. ej. commits ya creados, archivos modificados visibles al runner, fase explícita emitida por
un wrapper), se puede mostrar; **no es requisito de v1** y no debe degradar aislamiento.

### C. Etapas posteriores

Cuando Claude termina:
- Claude Live cambia a verificación;
- luego publicación;
- finalmente éxito/fallo real.

`VERIFY NOTHING` en una TASK que requiere implementación **no puede mostrarse como éxito**.
Revisar y endurecer el tratamiento del estado NOTHING para que el resultado visible sea
inequívocamente no exitoso. Si convertir el job global a failure requiere un cambio pequeño y
compatible con el contrato actual, hacerlo. Si existe una razón técnica seria para no hacerlo,
documentarla y al menos hacer que Claude Live marque FAILURE/NO_OUTPUT de forma inequívoca.

No romper las TASKs puramente documentales: el criterio correcto es que una TASK que efectivamente
produce cero commits no sea presentada como implementación exitosa. El protocolo/verificador debe
distinguir de forma segura lo que corresponda, sin inventar intención a partir del nombre del ID.

### D. GitHub Step Summary

Cada job relevante debe dejar un `GITHUB_STEP_SUMMARY` breve con:
- TASK;
- etapa;
- resultado;
- evidencia principal.

El summary no reemplaza el comentario vivo; lo complementa.

### E. Seguridad

Claude Live jamás debe mostrar:
- secretos o tokens;
- contenido de variables secretas;
- account IDs sensibles;
- prompts internos del proveedor;
- chain-of-thought;
- output completo oculto de Claude;
- material privado de propiedades;
- URLs firmadas o credenciales.

Puede mostrar:
- nombres de etapas;
- timestamps;
- duración;
- status/conclusion de jobs/steps;
- conteo de commits;
- conteo/lista acotada de archivos versionados;
- tests/resultados que ya formen parte de evidencia segura;
- rama/REPORT;
- errores sanitizados.

### F. Prueba

Añadir tests del contrato de Claude Live y una prueba reproducible que no necesite gastar una
segunda llamada real a Claude sólo para probar formato.

La propia ejecución M04 sirve como evidencia del ejecutor viejo; **no puede probar live durante sí
misma** porque el workflow modificado aún no está en `main`.

El REPORT debe decir exactamente qué falta para activar/probar Claude Live en una TASK posterior.

## No hacer

- NO exponer chain-of-thought.
- NO hacer streaming del output oculto de Claude.
- NO bajar el aislamiento bubblewrap.
- NO ampliar permisos más allá de lo mínimo necesario.
- NO imprimir secretos.
- NO tocar producto, landing, pricing, estilos, PRO, `src/` ni Railway.
- NO mergear a `main`.
- NO deploy.
- NO auto-merge.
- NO crear una UI externa si GitHub issue + Actions + summary resuelven v1.
- NO agregar servicios pagos.
- NO convertir “actividad” en una inferencia falsa.
- NO depender de que Joaquín tenga Terminal abierta.
- NO depender de ChatGPT para refrescar el estado durante la ejecución: GitHub debe sostener la
  señal por sí mismo.

## Acceptance criteria

1. Existe una superficie Claude Live identificable por TASK en el issue de transporte.
2. Se actualiza el mismo estado vivo en vez de spamear comentarios periódicos.
3. Durante un job Claude real en progreso puede mostrar heartbeat/tiempo transcurrido basado en
   estado observable.
4. Muestra gate, Claude, verificación, publicación y auditoría ChatGPT pendiente.
5. El estado final incluye commit count, file count, REPORT y rama cuando existen.
6. Los estados de fallo son visibles y no se maquillan como éxito.
7. `VERIFY NOTHING` deja de presentarse como ejecución exitosa de implementación; el REPORT
   explica la semántica exacta adoptada.
8. Jobs relevantes escriben `GITHUB_STEP_SUMMARY`.
9. No se expone output oculto, chain-of-thought ni secretos.
10. Permisos GitHub son mínimos y justificados.
11. Hay tests automatizados para parsing/render/update de estado y casos success/failure/nothing.
12. El aislamiento de M02.1 permanece intacto y sus tests relevantes pasan.
13. `git diff 6324b1f HEAD -- src/` vacío.
14. Sólo se modifican infraestructura/documentación/tests necesarios para Claude Live.
15. Existe `reports/M04_REPORT.md` y `CURRENT_STATE.md` actualizado.
16. Claude deja al menos un commit real.
17. Sin merge ni deploy.
18. REPORT identifica el paso exacto para activar v1 en `main` y la TASK de smoke posterior.

## Evidencia requerida

- Diff exacto.
- Lista de archivos modificados.
- Tests y resultados.
- Ejemplo renderizado del comentario Claude Live para:
  - queued;
  - Claude running;
  - verifying;
  - success;
  - failure / NOTHING.
- Evidencia de que se actualiza un mismo comentario.
- Ejemplo de `GITHUB_STEP_SUMMARY`.
- Permisos requeridos.
- Prueba de que no se imprimen secretos/output oculto.
- Prueba de que aislamiento/firebreak siguen vigentes.
- `git diff 6324b1f HEAD -- src/`.
- REPORT y CURRENT_STATE.
- Base propuesta para la siguiente TASK.
- Instrucción exacta de activación: qué commit/rama tendría que llegar a `main`, sin hacerlo.

## Decision gates

Si implementar heartbeat requiere elegir entre:
A) una solución GitHub-native simple y observable, o
B) reemplazar la arquitectura de ejecución / Claude Action por un sistema sustancialmente distinto,

elegir **A**.

Si la única forma de obtener “más detalle” exige exponer output oculto o chain-of-thought, no
hacerlo. Claude Live v1 puede limitarse a etapas y heartbeat real.

Cualquier cambio que implique un nuevo servicio externo, auto-merge, auto-deploy, reducción de
aislamiento o permisos amplios es `DECISION_REQUIRED`.

La activación en `main` es `MERGE_GATE`: Claude implementa y prueba en rama; ChatGPT audita;
Joaquín autoriza o rechaza el merge.
