# E42 — Pedido recibido → propiedad interna procesable

## Decisión aprobada

Cerrar la brecha que quedó entre E41 y el flujo operador existente.

Un pedido público de **Plano Corporativo** que está en `plano_requests` con estado `RECEIVED` debe poder convertirse, desde una superficie **interna protegida**, en una propiedad real del LAB reutilizando el plano ya subido.

Objetivo de negocio:
> el cliente sube el plano una vez; el operador no vuelve a descargarlo ni subirlo manualmente.

Esta TASK no entrega todavía el plano al cliente. Deja el pedido listo dentro del flujo existente para que la siguiente TASK produzca/entregue el Plano Corporativo.

## Problema

E41 recibe correctamente email + plano y persiste ambos, pero el pedido queda aislado en SQLite y disco. Para trabajar hoy habría que leer la base, buscar el archivo y volver a cargarlo manualmente al LAB.

E39 aprobó un flujo concierge inicial: pedido público simple → operador trabaja con el LAB existente → entrega. Debemos conectar esas dos mitades sin construir un CRM nuevo.

## Resultado esperado

1. Crear una vista interna mínima, protegida por el mismo HTTP Basic del LAB, para ver los pedidos de Plano Corporativo.
2. Mostrar sólo información operacional necesaria: referencia opaca, fecha, email, nombre de archivo, estado y vínculo a la propiedad interna si ya fue creada.
3. Un pedido `RECEIVED` tiene una acción única y clara: **PREPARAR EN LAB** (o redacción equivalente).
4. Esa acción:
   - crea exactamente una propiedad interna usando las abstracciones existentes;
   - copia/importa el plano persistido por E41 como el `FLOORPLAN_ORIGINAL` de esa propiedad mediante la capa de dominio existente, sin saltarse validaciones;
   - enlaza el pedido con esa propiedad;
   - cambia el estado del pedido a un estado honesto equivalente a `IN_PROGRESS`;
   - redirige al operador a la página existente de esa propiedad en el LAB.
5. La operación es idempotente: doble click/retry no crea dos propiedades.
6. Si la preparación falla a mitad, no debe declarar el pedido preparado ni dejar una segunda propiedad utilizable silenciosamente.
7. Un pedido ya preparado muestra/enlaza su propiedad; no vuelve a ofrecer crear otra.
8. No ejecutar automáticamente el motor desde esta acción. El operador entra al LAB y usa el flujo existente.
9. No exponer esta bandeja públicamente.
10. Mantener intacto el formulario público de E41.

Preferir reutilizar `properties`, `assets`, grants/entitlements y el flujo LAB ya existente antes que crear modelos paralelos.

## Acceptance criteria

1. Existe una ruta interna para pedidos de Plano Corporativo y responde 401 sin credenciales.
2. Con credenciales, lista pedidos E41 con referencia, fecha, email, archivo y estado.
3. Un pedido `RECEIVED` puede prepararse con una única acción POST protegida.
4. La acción crea una sola propiedad válida del LAB y reutiliza el archivo original como floorplan mediante la capa de dominio existente.
5. El pedido persiste `property_id` (o relación equivalente) y estado de procesamiento.
6. Tras éxito, redirige a la propiedad creada en el LAB.
7. Repetir el POST no crea una segunda propiedad.
8. Fallos simulados no dejan el pedido falsamente preparado.
9. El pedido ya preparado ofrece enlace a su propiedad, no un segundo botón de creación.
10. El POST no ejecuta motor ni abre red.
11. `/planos/solicitar` y su happy path de E41 siguen funcionando sin auth.
12. Tests nuevos cubren auth, listado, preparación, copia/import seguro, idempotencia, rollback/estado honesto y no ejecución de motor.
13. Tests relevantes E40/E41/LAB siguen verdes.
14. `git diff 6324b1f HEAD -- src/` vacío.
15. `reports/E42_REPORT.md` + `CURRENT_STATE.md` actualizados.
16. Al menos un commit real de implementación posterior al commit de TASK.
17. Sin merge, deploy ni movimiento de `main`.
