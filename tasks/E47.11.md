# E47.11 — Recuperación mecánica de H21: errores de proveedor seguros

## Decisión aprobada

Esta TASK recupera E47.10 sin cambiar su alcance ni semántica.

E47.10 implementó H21, pero el job de publicación la rechazó porque el diff generado contenía al menos un literal con forma de credencial. El guard del ejecutor funcionó correctamente: nada se publicó. La recuperación debe reimplementar H21 desde la última base publicada y evitar agregar cualquier literal que parezca secreto/token/key.

Joaquín ya aprobó H21.

## Problema

E46-H21 demostró que errores técnicos de proveedor pueden contener números largos, emails, teléfonos, rutas, request IDs u otros datos que el detector de PII interpreta como input humano.

Eso puede hacer que:

- una corrida FAILED termine bien en el motor pero falle al asentarse;
- settle() propague CampaignError;
- la página del caso o /panel respondan 500;
- el caso quede falsamente PROCESANDO;
- MEJORAR deje una propiedad huérfana si record() rechaza un error técnico.

## Resultado esperado

Cerrar H21 de forma mínima y segura:

1. Separar tratamiento de texto humano/no confiable del texto técnico generado por sistema/proveedor.
2. Mantener _no_pii o protección equivalente en todos los campos humanos.
3. Sanitizar de forma determinista el error técnico antes de persistirlo.
4. Cubrir al menos números largos/números con separadores, emails, teléfonos, rutas locales/temporales, identificadores largos, posibles secretos y textos excesivamente largos.
5. Si no puede sanearse con confianza, guardar error genérico seguro + clase/código.
6. settle() nunca debe romper panel/caso por el contenido textual de un error técnico.
7. CREAR FAILED hostil queda asentado, reintentable, executed=0, completed=0.
8. MEJORAR con error técnico hostil no debe producir 409/500 por PII técnica ni dejar huérfano atribuible al registro.
9. Panel/caso muestran mensaje útil pero seguro, sin rediseño.

### Regla especial del recovery: no disparar el detector de secretos del repositorio

NO agregar en ningún archivo un string literal que se parezca a una credencial real.

Para tests de sanitización de tokens/keys:

- construir el valor en runtime concatenando fragmentos inocuos;
- no escribir ejemplos completos de claves/tokens en comentarios, docstrings, fixtures, REPORT ni CURRENT_STATE;
- no incluir headers Authorization reales/simulados en forma literal;
- no incluir prefijos + payload largo que un secret scanner pueda interpretar como credencial;
- si se necesita demostrar el caso, describirlo semánticamente ("token sintético construido en runtime") y assertar que el valor construido no persiste.

Antes de commit, revisar el diff agregado buscando patrones con forma de secretos. Si el verifier podría interpretarlos como credencial, reescribir el fixture/documentación sin debilitar el test.

## Acceptance criteria

1. Error técnico con una secuencia larga de dígitos: settle no lanza, caso no queda PROCESANDO, caso GET 200, panel GET 200.
2. Repetir con:
   - número con separadores parecido a teléfono;
   - email sintético;
   - ruta/identificador largo;
   - texto excesivamente largo;
   - token sintético construido dinámicamente sin literal secret-like en el repo.
3. El evento persistido no contiene literalmente los valores hostiles que deban sanearse.
4. Conserva status/clase + descripción segura o código útil.
5. CREAR FAILED hostil: asentado, CAPTURED/reintentable, executed=0, completed=0; retry legítimo funciona.
6. CREAR DONE/E47.9 sin regresión.
7. MEJORAR con excepción técnica hostil no cae por PII ni deja huérfano por este defecto.
8. Comentario/prompt humano con email/teléfono sigue rechazado.
9. settle idempotente tras FAILED hostil.
10. Un caso hostil no derriba panel multi-caso.
11. E46 H21 E11/E11b/E11c o equivalentes explícitos pasan.
12. Suites focales E45/E46/E47 pasan, incluyendo H01/H02/H03/H05/H10/H16/H20/E47.9.
13. Cero llamadas pagadas.
14. reports/E47.11_REPORT.md + CURRENT_STATE mismo commit.
15. REPORT declara H21 PASS/PARTIAL/BLOCKED. Si PASS, HIGH/BLOCKER priorizados quedan cerrados y siguiente paso = E48 final readiness audit.
16. El diff final debe pasar el guard de secretos del ejecutor.
17. Sin deploy/merge.
