## Qué cambió

**Causa raíz.** `start_create`, `start_correction` y `start_improve` hacían «chequeo de eventos → crear
corrida/propiedad → registrar evento». El evento (`create_started`, `improve_started`) se escribe *después* de
crear la corrida y de que la web fije `confirm_paid=True`; entre leer y escribir dos peticiones simultáneas
pasaban las dos (E46 F4/F7: 2 corridas, 2 llamadas pagas, 2 propiedades).

**Mecanismo de claim.** `campaign._claim(case_id, nombre)` crea `cases/<id>/claims/<nombre>` con
`O_CREAT|O_EXCL`: el sistema de archivos lo concede a un solo llamador. Sin servicio externo, compatible con el
almacenamiento actual (archivos bajo `DATA_DIR/e44/`). El claim se toma **antes** de `create_initial` /
`create_correction` / `properties.create`, es decir antes de cualquier posible llamada paga.

| acción | claim | el perdedor |
|---|---|---|
| PROCESAR CREAR (`start_create`, y `run_create`) | `create` | `CampaignError` «ya fue lanzada» → 409 |
| CORREGIR (`start_correction`) | `correction_<n+1>` (n = correcciones ya asentadas) | `CampaignError` → 400 |
| PROCESAR MEJORAR (`start_improve`) | `improve` | `CampaignError` → 409 |
| MEJORAR publicar (`finish_improve`) | `improve_publish` | devuelve `None` (otra petición publica) |

MEJORAR **sí** compartía el defecto (F7: 2 propiedades), así que queda cubierto por el mismo principio.

**Recuperación legítima.** El claim se libera si la acción falla *antes* de dejar rastro (excepción al crear
la corrida/propiedad, fallo al registrar `improve_started`, motor sin credencial `BLOCKED_CRED`, fallo de
publicación). Para CORREGIR el número del claim cambia cuando `settle` asienta la corrección anterior (también
si falló), así que reintentar tras un fallo técnico sigue siendo posible. Los tests E46 de recuperación (E9,
E11c) pasan sin cambios.
